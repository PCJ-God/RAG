## 一、阶段评定：Modular

限定四档 `Naive / Advanced / Modular / Agentic`。

**判 Modular 的依据** `[读码]`

- `src/` 按 document / indexing / retrieval / generation / memory / safety / evaluation 分包，环节可独立替换；
- 9 个 `--no-*` 消融开关（guard / memory / intent / clarify / rewrite / decompose / tag / rerank / top_k）；
- 两路召回统一进可插拔重排（`DashScopeRerank` → `LLMRerank` 兜底）；
- local / DashVector 两套索引后端共用同一套 LlamaIndex 接口。

以上超出 Advanced RAG（仅做前后处理优化）的范畴。

**未到 Agentic 的原因** `[读码]`：`pipeline.query()` 的编排骨架是 Python 硬编码，LLM 只在 3 条预置分支里挑一个标签。缺口清单：

1. 无自主工具调用循环；
2. 无对召回结果的充分性自反思与重检索（self-RAG / CRAG 式 `is_sufficient` 回边）；
3. `_multi_pass` 的子答案不做覆盖度校验就 `merge`；
4. 检索次数、策略、top_k 由配置而非模型决定。

补上「检索 → 自评不足 → 改写再检索」的闭环，并让模型自主选工具与定步数，才可能改判 Agentic。

## 三、实测确认的缺陷（按严重度排序）

### D1 所有块 `header_path` 恒为空 ——「结构感知分块 / 精确到小节溯源」不成立 `[实测]`

本轮最严重的发现，此前双方都没注意到。实测输出：

```text
[loader] 加载 178 个文档
每文件 Document 数: {2_1: 36, 2_2: 20, 2_3: 39, 2_4: 43, 2_5: 40}
文档级元数据 keys: creation_date, file_name, file_path, file_size, file_type, last_modified_date
以 # 标题开头的 Document: 0/178
MarkdownNodeParser 后节点数: 178
带 header_path 的节点: 0/178 = 0%
```

根因链：

1. `loader.py` 用 `SimpleDirectoryReader(required_exts=[".md"])`，而该版本 `.md` 映射到 `llama_index.readers.file.MarkdownReader`（`file/base.py:85`）—— **不是一个文件一个 Document**；
2. `MarkdownReader` 自己已按标题切成 178 个 Document，且把标题**写进正文**、把 `#` **从标题里删掉**（`re.sub(r"#", "", key).strip()`），并且**不产生 `header_path` 元数据**；
3. 后续 `MarkdownNodeParser` 在任何 Document 里都找不到标题行（0/178），**实际是空转**（178 → 178 节点），既没做结构切分，也没生成 `header_path`；
4. `splitter.py` 的 `meta` 里 `str(section.metadata.get("header_path") or "")` 取到空串，写进**每一个块**；
5. `generator.py:_source_label` 的引用标签退化为 `[i]（file_name）`；`ask.py --show-sources` 的章节字段永远为空。

**影响面**：README 与《系统工作流程.md》中「标题路径自动写入块元数据（例如 `2.1 RAG工作原理 > 1. 建立索引`）」「引用溯源精确到小节」「语义切分继承 `header_path`」三处表述**与运行事实不符**。`header_path` 是本项目宣称的可解释性卖点之一，现在是空的。

**修复方向**（未实施）：改用 `SimpleDirectoryReader(input_files=[...])` 让每个文件产出一个完整 Document，再交给 `MarkdownNodeParser` 做标题切分——这才是文档所描述的链路。副作用：`MarkdownReader` 的「已经切好」这个隐性依赖消失，块数与现在完全不同，**必须重建索引并重跑全部评测**。

### D2 `_clean()` 的 HTML 剥离正则吃掉语料里的字面量标记 `[实测]`

`splitter.py:23` 定义 `_TAG_RE = re.compile(r"<[^>]+>")`，`_clean()` 对所有块文本做 `sub(" ")`。

```text
字面量 EOS 类特殊标记：清洗前 4 处，清洗后 0 处，丢失 4 处
  被清空的形态（按名，不含尖括号）：endoftext（出现 2 次）、return、im_end
  另有全角竖线形态的 end-of-sentence 标记同样被匹配清除
HTML 注释锚点命中：2_2 一处、2_4 三处
  贪婪的 [^>]+ 会从注释起始一路吞到下一个尖括号闭合
实测表格：178 个 Document 中仅 7 个仍含 Markdown 表格分隔行，0 个含 table 标签
```

**后果**：知识库正文里「各家模型终止符分别是什么」这段内容，被建库环节直接抹成空格——用户问到时，检索到的块里**根本不存在答案**。这不是排序不准，是数据被破坏，换 rerank 或换模型都救不回来。加上 `<!--` 锚点在 `2_4` 里跨行吞掉了含「拆解业务指标，可工程化衡量」的表格内容。全过程静默、无报错。

**修复方向**（未实施）：`_clean()` 收窄成只删真正的标签白名单（`table|tr|td|th|div|span|p|br|img|a|b|i|em|strong|code|pre|font|sup|sub` 等），HTML 注释改用非贪婪 `<!--.*?-->` 单独处理，竖线形态的特殊标记整体保护不碰。

### D3 标签路是「按标签取样」，不是「标签内语义检索」 `[读码]`

`retriever.py:_retrieve_by_tag` 的实际调用是 `collection.query(filter=f"tag='...'", topk=self.top_k * 2)`——**不传 vector**。`top_k=20` → 取 40 条该标签下的块，与当前 query 的语义相关性为零。

配套两个事实：

- `DashVectorStore.add` 用 `node_to_metadata_dict(node, remove_text=False, ...)`，正文进 `_node_content`，离线往返实测 `metadata_dict_to_node(doc.fields)` **能完整还原正文** `[实测]`。所以标签路不是死代码，它确实在往候选池里灌 40 条**与问题无关**的块。
- `_merge` 里标签路统一 `score=0.0`，判断条件是 `item.score > seen[node_id].score`，语义路余弦相似度基本为正 → 语义路恒胜出。

**更根本的问题**：`TAG_MAP` 的 5 个标签与 5 个文件一一对应，标签值等价于文件名，对检索**几乎没有信息量**。按标签过滤 ≈ 取出某个文件的全部内容，而这批块靠向量检索本身就能命中。所以「标签路增益不明显」的真正原因不是实现粗糙，而是**这个维度在当前语料上不存在有效信息**——外部那轮批评把因果归错了。

### D4 `_multi_pass` 的引用编号错位 `[读码]`

`pipeline.py:_multi_pass` 把各子问题的 `sources` 平铺 `extend`，再 `enumerate(..., start=1)` 重新编号；而子答案正文里的 `[i]` 是各 `_single_pass` 内部生成的编号。结果：**最终答案里的引用编号与 `sources` 列表对不上**，且 `sources` 未按 `node_id` 去重，同一块会重复出现。这直接破坏「答案可溯源」这个卖点。

### D5 评测结构上跑不到记忆与澄清 `[读码]`

`eval.py` 建 `RAGPipeline(domain=args.domain)` 不传 `session_id`；而 `pipeline.query()` 要求 `session_id` 与 `clarify_callback` 均非空才启用记忆和追问。所以**多轮、指代消解、澄清循环在评测链路里永远关闭**——不是指标少，是代码路径走不到。样本仅 6 条，`results.md` 里 `faithfulness=0.0` 占 3 条，在此 n 下任何对比都不具统计意义。

### D6 `--no-rerank` 路径无 top-k 截断 `[读码]`

关掉重排后，语义路 20 条 + 标签路 40 条 ≈ 60 个块**全部**拼进 prompt，没有任何截断。《系统工作流程.md》写的「粗排结果直接用于生成」字面准确，但后果没写：上下文暴涨，且正中参考资料里提到的「Lost in the middle」问题。

### D7 现有评测数字不可复现、不可归因 `[实测]`

`knowledge_base/` 目录不存在，而 `data/eval/results.md` 里有分数。也就是说这批数字**无法从当前仓库状态还原**：既不知道当时索引是什么，也不知道开关组合是什么。所以「把已有数字搬进 README」这个动作目前不成立——搬进去的是无出处的数字。

## 五、企业级 AI 知识库的架构结论

### 5.1 三条分水岭（其余都可以渐进补）

1. **权限必须前置到召回，不能事后过滤**：ACL 作为向量查询的 `filter` 下推。先召回再在应用层筛掉，无权限内容已经进了 LLM 上下文和日志，无法证明没泄露。改造点恰好是标签路那处调用——改成「带向量的 filter 检索」可同时修掉 D3 并打通 ACL 通道。
2. **引用必须由代码保证，不是 prompt 许愿**：生成时返回「编号 → node_id」映射，生成后校验答案里出现的 `[i]` 是否属于本次实际注入的编号集合，越界即判不可信并降级为拒答。这是「可问责」的前提，也是 D4 的根治法。
3. **准确率靠运营闭环，不靠换模型**：点踩 → badcase 队列 → 归因分类（内容错 / 检索没召回 / 生成跑偏）→ 分别修文档、修索引、修 prompt。参考资料给的节奏可采纳：**每周抽样审查 50 条**查询与回答。

### 5.2 十层参考架构（★ 为本轮新增或我此前漏掉的）

```text
① 部署形态决策   ★ 全托管 API / 专属版 / 本地推理 —— 决定后面所有层，必须最先定
② 接入层         网关 + SSO + RBAC + IM 入口
③ 编排层         会话状态机 / Agent 运行时（pipeline.py 退化为一个被调用的能力）
④ 数据工程层     连接器 → 解析(★表格与代码块的结构保护) → 分块
                 → ★生命周期(版本·TTL·软删除) → 元数据富化 → ★ACL 同步
⑤ 索引存储层     对象存储 + 向量库 + ★词法通道(BM25/稀疏) + 关系库(元数据/ACL/审计) + Redis
⑥ 检索层         ★ACL 前置 filter → 混合召回 → RRF(有排名可比之后) → rerank
                 → ★上下文预算 4~6k token，最相关块放两端
⑦ 生成层         模型路由(按难度分级) + ★引用程序化校验
⑧ 推理服务层     ★并发/量化/vLLM（仅当 ① 选本地推理）
⑨ 治理安全层     逻辑隔离 + 参数化 ACL + 脱敏 + 审计 + 注入防护
⑩ 评测运营层     第一天就积累的评测集 + 全链路 trace + badcase 闭环 + 成本看板
```

其中 ① 是本轮最重要的新增：当前 `config.py` 的 `BASE_URL` 指向公网兼容模式端点，意味着文档原文与用户提问整批送出公网。多数企业的第一条否决项就是这个，且它不是「加模块」能解决的，是部署形态选型——它会反推向量库、身份体系与成本模型。

### 5.3 元数据 schema 缺口

现有三字段 `tag / file_name / header_path`（且 header_path 实际为空）。企业级至少要富化到：
`source_uri · doc_version · owner · dept · acl · effective_date · ingested_at · trust_level · chunk_hash`，并配软删除标记、有效期降权、按 `doc_id + chunk_hash` 的幂等 upsert。

### 5.4 对那份参考文章（《企业级AI知识库的技术架构应该怎么设计？》）的评估

**它印证了我上一轮的判断**：效果上限取决于数据质量而非模型能力；渐进式落地（先一个部门一类文档跑通全链路）；评测要从第一天积累；上下文不是越长越好；查询路由分流。

**它补上了我漏掉的**：私有化与数据出域这个第一约束；推理服务层（量化 / PagedAttention / 投机解码 / 连续批处理）；解析质量决定上限这个坑；BM25 + RRF 的完整融合方案；六类异构存储的分工。

**必须打折使用的三点**：

1. **它是软文**。全文篇幅最重的两节（物理级数据隔离、混合云挂载）正好指向文末推荐的那家私有化厂商。技术内容大体真实，但**重心被商业动机扭曲**——它把这两个卖点写得比「知识生命周期治理」重要得多，而后者才是企业知识库的常态死因。
2. **它没有任何可引用的数字**。NDCG 0.58→0.76、表格准确率 60%→95%、成本降 40%、性能开销 10-15%、改造成本 3-5 倍——样本量、评测口径、基线定义一概没有。可以指导**方向**（分块策略影响很大），不能支撑**结论**。若把 0.76 写进 README，被追问一句就见底。
3. **有一处合规表述是错的**。它说逻辑隔离「无法满足等保三级及以上的要求」——等保 2.0 三级要的是访问控制、审计、数据保密性与完整性，**不强制按密级分物理卷**；强制物理隔离的是涉密系统的**分级保护**，是另一套标准。它的客户是制造业 + 军工订单，那个场景确实要物理隔离，但外推成通用要求不对。照抄会在安全评审上被抓住。

**对你的规模属于过度设计、我建议不跟的**：

| 它的做法 | 它的前提 | 你的现实 |
| --- | --- | --- |
| 物理级隔离（分磁盘卷 + VLAN + 多套向量库实例） | 涉密验收必须项 | 无涉密需求，做 ACL 前置下推即可 |
| Kafka 解耦采集与处理 | 多源并发 + 有运维值班 | 5 个静态文件，只需「解耦思想」：任务表 + 幂等 upsert |
| Neo4j 知识图谱 + NER/RE 抽取 | 有专职人力 | **它自己都承认是坑**（自动抽取准确率约 70%，需长期人工审核） |
| Qwen2-72B + 4×A100 自部署 | 私有化合规 + 百万级硬件预算 | API 按 token 付费；但要吸收它的**模型路由**思想（你已有 qwen-plus / qwen-turbo 两份对比 CSV 可作起点） |
| 混合云挂载 + 冷热分层 | 已有 OSS + 机房 NAS | 无 |

**它没写、但我坚持的**：知识生命周期治理（TTL、软删除、版本冲突处理）、属性级 ACL、审计留痕。全文对这些只字未提，因为安全部分全押在物理隔离这一个卖点上——这正是 5.4-1 说的重心扭曲。

## 六、三条路线

| 路线 | 内容 | 工作量 | 产出 |
| --- | --- | --- | --- |
| **R0 最小诚实** | 只修已确认的真实缺陷（D1~D7）+ 让评测可复现可发布；README 删掉企业级暗示 | 2~3 天 | 一个干净的 Modular RAG，文档与代码一致 |
| **R1 纵深**（我推荐） | R0 + 把「权限前置判定」和「引用可验证」两件事做透到可被追问。**明确不做**：连接器 / Kafka / 知识图谱 / 混合云 / 物理隔离 / 自部署 / 增量同步 | 1.5~2 周 | 别人项目里没有、且**不靠语料规模撑着**的那一层；可现场演示「同一问题、两个身份、各自合规的不同答案」 |

**R1 之所以成立而不空**：ACL 与 tag 的区别是关键。tag 在你的语料上等价于文件名，信息量为零；而 ACL 是**人造也有信息量**的——同一份文档，A 用户可见、B 用户不可见，检索结果必须不同，且这个差异不来自目录结构。所以「权限判定」这件事在小语料上依然能被严格验证（配越权测试用例），而「标签检索」不能。

**R2 的前提已被你否决**：你在本轮明确说了「真实数据：`data/knowledge/rag`」。所以除非你改变这个决定，R2 不在选项内——这一行留着是为了让「为什么不走 R2」有记录。
